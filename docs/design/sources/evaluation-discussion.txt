1. Granularity: claude.ai tab vs Claude Code in herdr

Trace the same task (jobapp-sensemesh, "draft the follow-up") through both:

Claude Code in herdr

open → terminal exec → claude starts → SessionStart hook → agent.* events with session_id, cwd, transcript_path
prompt → working; permission prompt → blocked; Stop → idle; SessionEnd → released
optional, and cheap: PostToolUse for Write/Edit/Bash gives you which files the session touched, deterministically
the full transcript is on disk (~/.claude/projects/<slug>/<session>.jsonl), so a close-summary can be derived, not typed

claude.ai tab

chrome observer: targetCreated at claude.ai/new, then targetInfoChanged when the URL becomes /chat/<uuid> and the title becomes the conversation name
focus: from Hyprland, not CDP (see below)
state: none. Content: none. The draft leaves via clipboard and Heimdall never sees it
chat.summarized only if you type one

So the two sessions sit on different observability tiers, and the doc should say so explicitly rather than let surface_state.agent_state be silently null for chats. Proposed contract per surface kind:

tier	what	tab/chat	terminal/agent	repo
0 existence	observed/opened/closed	auto	auto	manifest
1 attention	focus spans	auto	auto	via agent tool events
2 state	agent.*	—	auto (hooks)	—
3 content	chat.summarized, capture	manual	derivable from transcript	—

The principle: log what the source can vouch for, at the source's resolution, and never synthesize a finer event (no inferring "email sent" from a Gmail title change). Consequences and fixes:

Tab ≠ surface. A CDP target id is stable across navigations; your surface id (sha256(kind|pointer)) is not, and chat vs tab for the same URL yields two ids. Make the surface the pointer, the tab a container_id in the payload, and navigation = surface.closed(old) + surface.opened(new, container_id). Derive kind from the pointer by rule (claude.ai/chat/* → chat) so the id is deterministic. Normalize pointers (strip fragments, tracking params) or the same page gets N ids.
Tab switch detection. Target.setDiscoverTargets doesn't report activation; targetInfoChanged only fires on URL/title changes. The signal you actually have is Hyprland's activewindowv2 + windowtitle on the Chrome window, matched by title to the CDP target. Say so in §6, and note it fails on duplicate titles (two "New chat" tabs).
touched floods. activewindow fires on every focus change. Record focus spans (surface.focused{duration_s} on blur, debounced) instead of point touches. Same information, ~50× fewer rows, and it's what last_touch and staleness need anyway.
Blocked has no exit. Approving a permission prompt doesn't fire UserPromptSubmit, so a session shows blocked for the whole tool run. Map PostToolUse → working. Also Notification fires for idle nags, not just permissions; filter on the payload.
Session→task binding. cwd→repo→task breaks the moment two tasks share a repo (worktrees, monorepo). The viewport controller launches the terminal, so it can name the task; but if herdr is a server/attach model like tmux, the pane's shell inherits the server's environment, not the client's, so an env var set at exec time won't arrive. Two options: herdr exports its workspace name into panes (question below) and the hook reads it, since herdr workspace = task id; or the hook posts git rev-parse --abbrev-ref HEAD and the manifest's branch disambiguates. Keep cwd as fallback.
Make the summary the equalizer. A notifier rule: closing a chat surface with > N min of focus and no chat.summarized is needs-you. For Claude Code, derive the summary from the transcript via the intent-extraction function. For claude.ai, if you want more than typed summaries, a user-triggered bookmarklet that grabs the conversation DOM and POSTs to /summary is different in kind from the scraping you rejected: it's on-demand, not a state watcher, and when the selector breaks you fall back to typing.
2. Fulfillment: how does Heimdall know the email went out?

It doesn't, and shouldn't pretend to. The architecture already has the right answer: observers produce evidence, a matcher binds evidence to a task, ratification decides. Today done: Reply received or 14 days of silence is prose, so nothing can match it. Split it:

yaml
done:
  text: Reply received or 14 days of silence
  checks:
    - {kind: mail.received, from: "@sensemesh.com"}
    - {kind: silence, days: 14, after: subtask:email}
subtasks:
  - {id: email, title: send email, check: {kind: mail.sent, to: "@sensemesh.com"}}

Flow: a mail observer emits surface.observed{kind: mail, msgid, from, to, subject, folder} → a deterministic matcher evaluates every open check against each event → proposal.created{kind: fulfill, task, subtask, evidence: [event_ids]} → ratify → task.updated. The silence check is just commitment.created{due: +14d} anchored on the ratified send, reusing machinery you have. Check kinds for v1: manual (default), silence, mail.sent, mail.received, agent.released, repo.commit (a post-commit hook installed by init --hooks, same pattern as Claude Code's). gh.pr_merged is a configured adapter later.

Two notes: mail is already in your surface-kind enum but has no observer in §6, so this is filling a hole you left, not adding scope. And keep the ratify step even for "obvious" matches; one keypress is cheap and it's what keeps the log honest. If you want to defer the mail observer, v1 = manual + silence still improves on today, because the timer runs without you.

The pipeline is then uniform: a sensor emits session.ended{kind, session_id, transcript_ref, turns, artifacts[]} (deterministic, no inference), the daemon runs intent extraction over the transcript if a provider is configured and emits chat.summarized{decided, next_action, resume_by, drop_if, artifacts}, and that becomes a proposal.created{kind: next_action} if the session is bound to a task, or classifier input if not. Codex specifics. Codex has two mechanisms and they don't overlap. 2. Extension and mail

Yes to the extension, with a specific scope. The handoff rejected the Obsidian clipper as a second writer with no origin. A first-party MV3 sensor that posts to the daemon isn't that. It consolidates four needs: capture (kills the bookmarklet's CORS/Local-Network-Access problem outright), tab focus via tabs.onActivated (replaces the Hyprland title-match hack), and content sensors for claude.ai and chatgpt.com. For content, don't scrape the DOM: have the extension ask the page's own backend for the conversation JSON, the same call the page makes. Still unofficial, so contain it: per-site adapters versioned independently, a self-test that emits sensor.degraded when the shape drifts, and nothing downstream that depends on it for correctness — it produces evidence for proposals, never state transitions. That's a defensible narrowing of the scraping objection: the fragility is isolated and loud, and the alternative is no signal at all.

Keep CDP as the actuator for v1 (open/close need a synchronous channel and it's already specified); the extension is the observer. Consolidating both into the extension would drop the websocket dependency and the launch flag, but needs a reverse channel to a service worker that sleeps. Revisit after M1b.

Mail: the client is irrelevant; the mailbox is the source. A native client emits nothing; it just reads the same IMAP account Gmail-in-a-tab does. So one mail observer covers both populations: IMAP IDLE on Sent and INBOX (Gmail with an app password, Workspace with XOAUTH2), or inotify on a local maildir for mbsync/notmuch users, which is stdlib-only. Emit surface.observed{kind: mail, msgid, from, to, subject, folder} and let done.checks match. Go has no stdlib IMAP: either add github.com/emersion/go-imap/v2 to the allowed list or hand-roll the five commands you need. A Gmail API/OAuth path is the "many users" answer but requires a verified OAuth app; that's a scale-path row, not v1. An extension watching Gmail's DOM is the worst of the options — skip it.

5. Streams, tasks, types

Not quite — what you're describing ("the discrete steps required to achieve completion") is the type, not the stream. Three words, three jobs:

Task — the unit of ranking, membership, and completion. Can have a parent. job-search is a parent task (type project, or the initiative the classifier proposes); jobapp-sensemesh is a child (type application). Both are tasks; both are ranked.
Stream — an address for routing captures and surfaces. Every task id is a stream address; unassigned is the only other one. Addressing something to job-search means "belongs here, not yet assigned to a child," and the classifier proposes the child. The tasks.yaml field currently named stream: is a parent pointer and should be renamed parent: so the word means one thing.
Type — a workflow template: the status lifecycle plus default subtasks with their checks. Move this out of the enum in §4.3 into types.yaml, so add --type application scaffolds research → draft → send → follow-up with checks attached and a status mapping (submitted ⇐ subtask send done).

Planner rules for the hierarchy: score leaves; subtasks inherit importance and impact from their task, take urgency from their own due else the task's resume_by, and carry their own estimate_minutes. A task's next_action is its first open, unblocked subtask in authored order (after: for explicit dependencies); sequence usually matters more than score among siblings, so don't rank them unless asked. A parent's score is the max over its children, and its completion is {kind: children_done}. The plan shows parent › task › subtask paths. That establishes the hierarchy without the planner inventing one.
